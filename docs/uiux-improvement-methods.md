# Claude Code 로 UI/UX 를 개선하는 방법 — 바이브 코딩 실전

Claude 로 화면을 개선하는 방법을 묻는 질문의 답은 프롬프트 문구가 아니다.
**① 모델이 자기 결과물을 눈으로 보게 만들고 ② 취향을 검사기로 바꾸는 것** — 이 둘이 전부다.
이 저장소는 ②를 이미 갖췄다(`design/check_design.py`). 이 문서는 ①의 절차와,
그 위에서 쓰는 바이브 코딩 요령을 적는다.

> 이 문서는 방법론이다. 값·치수·완료 정의의 정본은 여전히
> `design/ggc-tokens.css` 와 `docs/23-…-단일디자인-계약.md` 다. 여기 값을 적지 않는다.

## 1. 원칙 — 모델이 화면을 봐야 개선이 된다

코드만 고치고 렌더 결과를 보지 않는 세션은 UI 개선이 아니라 CSS 편집이다.
LLM 은 자기가 만든 화면의 결함(겹침 · 오버플로 · 어긋난 정렬 · 빈약한 여백)을
**텍스트로는 못 보고 스크린샷으로는 잘 본다.** 그래서 루프가 이렇다:

```
렌더 → 스크린샷 → 비평(무엇이 왜 나쁜가) → 수정 → 재촬영 → 비교
```

- **촬영 뷰포트는 계약과 같게 한다** — 1440×900 · 390×844 (확폭 채택 시 1920×1080).
  개선 루프와 `G-DESIGN` 증거가 같은 프레임을 보게 되어 증적이 그대로 재사용된다.
- **도구는 Playwright MCP 또는 Chrome DevTools MCP** 를 쓴다. Claude Code 에 붙이면
  모델이 직접 열고 · 찍고 · 콘솔을 읽는다. 망분리 환경에서는 브라우저 바이너리를
  로컬에 두고 쓴다 — 이 루프에 외부 요청이 필요한 단계는 없다.
- **콘솔도 루프 안에 넣는다.** `G-DESIGN` 의 "콘솔 0건" 을 마지막에 몰아 확인하지 말고
  매 재촬영마다 같이 읽게 한다. 마지막에 발견한 콘솔 오류가 가장 비싸다.

정적 HTML(이 저장소의 `design/examples/`)은 서버 없이 파일로 열리므로 루프가 가장 싸다.
서비스 화면은 해당 스택의 dev 서버를 띄우고 같은 루프를 돈다.

## 2. 반복되는 디자인 작업은 스킬로 만든다

바이브 코딩의 실패 형태는 "그때는 잘 됐는데" 다 — 잘 되게 만든 프롬프트가 세션과 함께
사라진다. **재현되어야 하는 절차는 스킬(SKILL.md)로 굳힌다.** 이 저장소의
[`skills/ggc-design/`](../skills/ggc-design/SKILL.md) 이 실례이고, 구조에서 배울 것은 셋이다:

- **frontmatter `description` 이 트리거다.** "디자인 입혀줘" · "이 서비스만 색이 다르다"
  같은 실제 요청 문구를 넣어야 스킬이 제때 물린다.
- **본문은 절차, `references/` 는 참조.** 매번 읽을 것과 필요할 때 읽을 것을 나눠야
  컨텍스트가 버틴다.
- **첫 명령이 검사기다.** 스킬이 문서 낭독이 아니라 실측으로 시작하게 한다.

Anthropic 공개 스킬 저장소(`github.com/anthropics/skills`)에 프런트엔드 디자인 ·
아티팩트 제작 계열 스킬이 있다. 그대로 쓰기보다 구조를 참고해 조직 스킬을 만드는
쪽이 맞다 — 범용 스킬은 "새 색을 만들지 않는다" 같은 조직 계약을 모른다.

## 3. 만드는 손과 비평하는 눈을 분리한다 — 디자인 리뷰 서브에이전트

같은 컨텍스트 안에서 만들고 스스로 평가하면 관대해진다. **리뷰는 별도 컨텍스트의
서브에이전트에게 시킨다** — `.claude/agents/design-reviewer.md` 로 정의해 두면
"리뷰해줘" 한 마디로 물린다. 이 조직에 맞는 골격:

```markdown
---
name: design-reviewer
description: 화면 스크린샷과 소스를 받아 공통 디자인 계약 위반과 UX 결함을 리뷰한다
tools: Read, Grep, Glob, Bash
---
스크린샷(1440·390)과 해당 화면 소스를 받는다. 다음 순서로만 판정한다.
1. 기계 판정 먼저 — check_design.py --report 출력을 읽고 FAIL/WARN 을 요약
2. 계약 판정 — 셸 3종 유무 · archetype 처방 순서(references/archetypes.md) 준수
3. 상태 판정 — 빈 상태·오류·로딩 3종이 화면에 있는가
4. 시각 판정 — 정렬 축 이탈 · 여백 리듬 붕괴 · 행 높이 불일치 · 오버플로
5. 각 지적에 심각도(계약위반/UX결함/취향)를 붙인다. 취향은 수정을 강제하지 않는다
새 색·새 컴포넌트 제안은 금지. 개선안은 정본 토큰과 기존 마크업 재사용으로만 낸다.
```

핵심은 마지막 두 줄이다 — 리뷰어에게 **발명 권한을 주지 않는다.** 리뷰 에이전트가
"더 산뜻한 색" 을 제안하기 시작하면 그게 열 번째 드리프트다.

## 4. 바이브 코딩 요령 — 프롬프트에서 갈리는 것

1. **레퍼런스를 먼저 보여준다.** 화면을 짜기 전에 `design/examples/` 를 열어 보게 한다
   (스킬 Phase 4 와 같다). 모델은 "이런 느낌" 이라는 말보다 실물 DOM 에서 훨씬 정확히 베낀다.
2. **형용사가 아니라 판정 가능한 문장으로 요구한다.** "예쁘게 · 모던하게 · 깔끔하게" 는
   모델마다 다른 화면이 된다. "카드 간격을 한 단계로 통일 · 숫자는 우측 정렬 ·
   제목 계층은 2단계까지" 처럼 맞았는지 확인 가능한 문장이 되어야 루프가 수렴한다.
3. **한 번에 한 축만 고친다.** 간격 → 타이포 → 색 순서로 축을 나눠 돌린다. 전부를
   한 턴에 시키면 좋아진 것과 나빠진 것이 섞여 되돌릴 수 없다. 리스킨에서 기준선을
   먼저 고정하는 것과 같은 이유다.
4. **갈림길에서는 3안을 만들게 해서 고른다.** 어느 방향이 맞는지 말로 고르지 말고
   같은 화면의 변형 3개를 만들어 스크린샷으로 비교한다. 고른 뒤 나머지는 지운다 —
   남겨 두면 드리프트 씨앗이 된다.
5. **before/after 를 나란히 요구한다.** 개선 턴마다 전후 스크린샷을 함께 받으면
   "좋아졌다" 가 주장이 아니라 증거가 된다. 리스킨 시각 회귀 비교와 같은 형식이다.
6. **점수보다 감점 사유를 요구한다.** "10점 만점에 몇 점" 은 장식이다. "감점 사유를
   심각도순으로, 각각 수정 방법과 함께" 가 다음 턴의 작업 목록이 된다.
7. **이 조직에서는 '독창적으로' 를 금지어로 쓴다.** 일반 바이브 코딩 가이드는 AI 스러운
   화면을 벗어나려 발명을 권하지만, 여기의 목표는 반대로 **수렴**이다. 발명이 필요하면
   정본에 먼저 넣는다 — 화면에서 발명하지 않는다.

## 5. 취향을 게이트로 바꾼다

루프에서 배운 것 중 다음에도 지켜져야 하는 것은 사람 기억이 아니라 기계에 넣는다.

| 어디에 | 무엇을 |
|---|---|
| `CLAUDE.md` | 세션마다 상속돼야 하는 원칙 — "새 색 금지 · 토큰 먼저 로드 · 3종 상태 필수". 모든 세션이 읽는 유일한 자리다 |
| `check_design.py` | 판정 가능해진 규칙. "그러지 말자" 가 세 번 반복되면 검사가 될 차례다 |
| 훅 (PostToolUse) | CSS·HTML 편집 직후 `--report` 자동 실행. 위반을 커밋 전이 아니라 편집 직후에 잡는다 |
| CI | `--gate` + exit 1. 사람이 잊어도 병합이 막힌다 |

이 저장소의 역사가 근거다 — 정본 문서와 파일이 두 달간 어긋나 있었고, 그것을 해소한 것은
더 좋은 문서가 아니라 D6 검사였다. **프롬프트로 얻은 품질은 게이트에 넣어야 다음 세션에도 있다.**

## 6. 도구 지도 (2026-08 기준)

| 도구 | 무엇에 쓰나 | 망분리 |
|---|---|---|
| **Playwright MCP / Chrome DevTools MCP** | §1 의 스크린샷·콘솔 루프. 개선 작업의 본체 | ○ 로컬 브라우저로 가능 |
| **Claude Design** (`.dc.html` 캔버스) | 초안을 시각 편집으로 다듬은 뒤 코드로 이식. 이 시스템의 디자인 원본 8개가 이것 | △ 편집은 클라우드, 산출물은 로컬 |
| **스킬 (SKILL.md)** | 재현돼야 하는 절차의 고정. `ggc-design` 이 실례 | ○ |
| **서브에이전트** (`.claude/agents/`) | §3 리뷰어처럼 역할 분리 | ○ |
| **Figma MCP** | 디자이너가 그린 파일을 코드로. 디자이너 협업이 생기면 검토 | △ Figma 접근 필요 |
| **anthropics/skills 공개 스킬** | 구조 참고용. 조직 계약을 모르므로 그대로 쓰지 않는다 | ○ 반입 후 |

`.dc.html` 을 다룰 때의 함정(런타임 전용 `style-hover` · 반응형/접근성 부재)은
[`references/porting.md`](../skills/ggc-design/references/porting.md) 가 정본이다.

## 7. 이 저장소에서의 착지 — 무엇이 이미 있고 무엇이 이 문서인가

| 방법 | 구현체 |
|---|---|
| §1 스크린샷 증거 | `references/verify.md` — `G-DESIGN` 이 이미 요구한다 |
| §2 스킬 | `skills/ggc-design/` |
| §4-1 레퍼런스 | `design/examples/` 갤러리 5쪽 |
| §5 게이트 | `check_design.py` 6종 검사 |
| §1 개선 **루프** · §3 리뷰 분리 · §4 프롬프트 요령 | **이 문서가 채우는 자리** — 검증(사후)만 있었고 개선(과정)의 절차가 없었다 |

요컨대 이 저장소는 "잘못되면 잡는" 쪽이 두껍고 "좋아지게 만드는" 쪽이 얇았다.
좋아지게 만드는 쪽은 도구가 아니라 습관이다 — **보게 하고, 한 축씩 고치고, 남길 것은
게이트에 넣는다.**
